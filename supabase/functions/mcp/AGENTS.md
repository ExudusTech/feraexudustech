# mcp (Flora) rules
- MCP request auditing is service-role-only and runs as background work so audit failures cannot change client responses.
- Normalize MCP tool parameters centrally inside the router, leaving the received request untouched so auditing retains original input.
- Apply trusted chat-channel enrichment centrally after parameter normalization without mutating received requests, so all tools agree while auditing retains original input.
- Select MCP coverage centrally by exact region, narrowest matching CEP interval, then the region of the single establishment located in the same chat; a city with several regions and no selector returns precisa_localizar (no dates) so districts are never mixed.
- Keep establishment provider requests server-side, bounded, sequential and cached with graceful fallbacks so Google failures cannot interrupt Flora conversations; persist CEP in the existing lead zip_code column to avoid duplicate address fields.
- Keep establishment name matching and short-address confirmation local to the lookup tool, and separate biased/unbiased cache entries, so shared parameter normalization and other tools remain unchanged.
- Product/location contact enrichment selects only tenant phone-matched nome without writing person records.
- Coverage binding inference stays local to verificar_cobertura_regiao, and outside-coverage registration uses tenant-scoped select plus insert/update without global interaction uniqueness, so other tools and tenants remain unaffected.
- Human handoff always resolves or creates a tenant-scoped lead, records the note in lead_timeline (description untouched), and alerts per lead at most once per 30 minutes, with high-urgency follow-ups limited to one per 15 minutes, so transfers stay visible without spamming the team.
- MCP tools return generic "Erro interno ao <ação>" for database failures and log only stage and error code server-side.
- Lead timeline (lead_timeline) holds short masked summaries only, written by mcp in background on the company-isolated lead; context returned to Flora is built from the chat-identified person only (phone / instagram_user_id / messenger_id), so transcripts and other people's data never leave the Fera.
- localizar_estabelecimento answers precisa_nome without any provider call when the name is only a generic business type, so Flora never offers lookalike places.
- consultar_rota_consultor computes opcoes_horario server-side (3 distinct days, band start to end minus visit duration, skipping the area consultant's existing schedules) so Flora never invents out-of-band times.
- A visit whose client asked to reschedule is cancelled by an AFTER INSERT trigger on schedules, so the old and new visit can never both stay active.
- Booking moves the lead only through stage_id ("Visita agendada"); the database trigger keeps the legacy stage column in sync.
- Google Calendar is read-only (GET only, test-enforced): all-day/holiday blocks come from the holidays table (source='google', synced by google-calendar-sync daily + on demand), timed Flora events are read live with a 5-min in-memory cache and fall back to google_calendar_busy, so Google failures never block Flora.
- localizar_estabelecimento treats a name as generic only when nothing remains after removing business types, articles/prepositions/possessives and the city phrase.
- flora_equipe is a thin dispatcher: it resolves the team user from chat_id first, interprets free fields server-side, then calls the existing TEAM_TOOLS entry and adds mensagem_para_equipe, so individual team tools stay the single source of behavior.
- localizar_estabelecimento, consultar_rota_consultor and agendar_visita_tecnica reuse verificar_cobertura_regiao before searching or offering times; only DISTRIBUIDORA searches or promises a visit, SEM_COBERTURA registers once per chat_id, so out-of-area leads never reach scheduling.
- Every city comparison (coverage, routes, bookings, holidays, lead reuse) goes through CITY_ALIASES + cityKeys/sameCity/cityInArea, with areas filtered in code rather than SQL ilike, so aliases like "Búzios" always reach the registered area.
- anexar_coleta/registrar_nota without an open visit go through visitaRelatada: offer + HMAC codigo_confirmacao over user/empresa/cidade/texto, then the coverage check (DISTRIBUIDORA only), client or open lead reuse by normalized name + sameCity, and a concluded primeira_visita with source flora_relatada and no check-in, so reported visits never duplicate companies.
- flora_equipe indicadores resolves period (São Paulo calendar + equivalent previous period) and seller/city/type slices server-side, forcing field roles to their own numbers; the boletim PNG is SVG rendered by resvg-wasm with the embedded Montserrat (_shared/boletim-fonte.ts) loaded through dynamic imports, falling back to graficoPng, so the test harness (no imports) still runs and a renderer failure never blocks the text answer.
- contexto_qr/registrar_avaliacao_qr resolve the 'ref Q…' through the embedded qr block (identical to _shared/qr.ts, test-enforced), classify the chat as EQUIPE (profile phone), CLIENTE (person linked to the device's company) or PUBLICO, return no ids, contacts or label number to PUBLICO, and send low-rating alerts in background to avaliacao_qr_baixa subscribers plus the client's consultant.
- Matriz handoffs branch inside solicitar_atendimento_humano (alias transferir_para_humano) before any atendimento/precisa_humano write, and alert gestor/matriz-role users through dispatchTeamNotification extraRoles (profiles.phone, deduped), so a Matriz lead is never parked waiting for the Distribuidora.
- Smell words in consultar_produto route to the aromatização/neutralização categories (Ekkoa first) after brand/name matches and only when no other word names a different product line.
